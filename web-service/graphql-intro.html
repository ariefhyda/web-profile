Pertemuan 9: Pengenalan GraphQL — Konsep Dasar

Estimasi: 75 Menit
Teori & Konsep

Video: Mengapa GraphQL?

Klik untuk memutar

REST sudah hebat — tapi tidak sempurna. Saat aplikasi mobile butuh data dari banyak resource sekaligus, REST sering memaksa kita melakukan beberapa request atau menerima data yang lebih banyak dari yang diperlukan. Inilah celah yang diisi oleh GraphQL: bahasa query yang memungkinkan klien meminta tepat data yang dibutuhkan, dalam satu request.

Capaian Pertemuan Ini

Mahasiswa mampu (1) menjelaskan masalah over-fetching & under-fetching pada REST, (2) memahami konsep Query & Mutation di GraphQL, (3) membaca Schema Definition Language (SDL), dan (4) memutuskan kapan GraphQL lebih cocok daripada REST.

Masalah REST yang Diselesaikan GraphQL

📥
Over-fetching — Terlalu Banyak Data

Endpoint GET /api/users/12 mengembalikan semua field user: nama, email, alamat, riwayat login, preferensi notifikasi, foto profil, dll. Padahal layar mobile hanya butuh nama & foto. Bandwidth terbuang sia-sia, render lebih lambat.

📤
Under-fetching — Harus Berkali-kali Request

Untuk menampilkan satu post + author + komentar + balasan komentar, klien harus memanggil 4 endpoint REST berbeda. Setiap request = round-trip jaringan = latensi. Total = lambat.

🔀
Versioning yang Berantakan

Saat layar mobile butuh field baru, REST sering melahirkan /api/v2/users dan menjaga v1 agar klien lama tidak rusak. Repot mempertahankan beberapa versi paralel.

Demonstrasi: Halaman "Detail Mahasiswa" di Mobile

Misalkan layar mobile menampilkan: nama mahasiswa, nama prodi, dan 3 nilai terakhir. Mari bandingkan beban request REST vs GraphQL.

Dengan REST — 3 Round-Trip

1 GET /api/mahasiswa/12 → ambil seluruh data mahasiswa (over-fetch)
2 GET /api/prodi/{prodi_id} → ambil detail prodi
3 GET /api/mahasiswa/12/nilai?limit=3 → ambil 3 nilai terakhir

Dengan GraphQL — 1 Round-Trip, Field Tepat

📝 Query (dikirim klien)
query {
  mahasiswa(id: 12) {
    nama
    prodi {
      nama
    }
    nilai(limit: 3, sort: "-tanggal") {
      mataKuliah
      nilai
    }
  }
}
✓ Response (dari server)
{
  "data": {
    "mahasiswa": {
      "nama": "Siti Aisyah",
      "prodi": { "nama": "Teknik Informatika" },
      "nilai": [
        { "mataKuliah": "Web Service", "nilai": 87 },
        { "mataKuliah": "Data Mining",  "nilai": 91 },
        { "mataKuliah": "Mobile Prog.", "nilai": 84 }
      ]
    }
  }
}

Perhatikan: response mengikuti bentuk query persis. Tidak ada field email, alamat, atau foto — karena klien tidak memintanya. Inilah "ask for what you need, get exactly that".

Apa itu GraphQL?

GraphQL adalah bahasa query untuk API + runtime untuk mengeksekusi query, dirilis Facebook pada 2015 setelah dipakai internal sejak 2012. Ia bukan database, bukan ORM, dan bukan pengganti HTTP — ia adalah lapisan kontrak di atas server Anda yang memungkinkan klien mendeskripsikan data yang diinginkan dengan tepat.

🍱
Analogi: Prasmanan vs Set Menu

REST seperti set menu — chef sudah memutuskan tiap paket berisi nasi, ayam, sayur, soup. Anda terima semua meski hanya butuh ayam. GraphQL seperti prasmanan — Anda ambil tepat porsi nasi, secuil ayam, satu sendok sayur, lewati soup. Tidak ada yang terbuang.

Karakteristik Inti GraphQL

  1. Satu endpoint — Biasanya POST /graphql. Tidak ada lagi puluhan URL berbeda.
  2. Klien menentukan bentuk response — Server hanya menyediakan kapabilitas; klien yang memilih field.
  3. Strongly-typed schema — Setiap field dan tipe didefinisikan kontrak. Validasi otomatis.
  4. Introspection — Klien bisa "bertanya" ke server: "field apa saja yang tersedia?". Inilah dasar tools seperti GraphiQL & Apollo Playground.
  5. Versioning organik — Tambah field baru tanpa merusak klien lama (mereka tidak meminta field baru = tidak terdampak). Deprecation per-field, bukan per-API.

Tiga Operasi GraphQL

Operasi Tujuan Analog REST
Query Membaca data GET
Mutation Membuat / mengubah / menghapus data POST / PUT / PATCH / DELETE
Subscription Realtime — server push data ke klien saat ada perubahan (REST tidak punya — biasanya WebSocket terpisah)

Schema Definition Language (SDL)

Sebuah server GraphQL mengekspos schema: deklarasi semua tipe dan operasi yang tersedia. Schema ditulis dalam SDL — bahasa deklaratif yang mudah dibaca. Inilah kontrak tunggal antara backend dan semua klien.

schema.graphql 
type Mahasiswa {
  id: ID!
  nim: String!
  nama: String!
  email: String!
  prodi: Prodi!
  nilai(limit: Int = 10, sort: String): [Nilai!]!
}

type Prodi {
  id: ID!
  nama: String!
  jenjang: String!
  mahasiswa: [Mahasiswa!]!
}

type Nilai {
  mataKuliah: String!
  nilai: Float!
  tanggal: String!
}

# Operasi yang bisa dilakukan klien
type Query {
  mahasiswa(id: ID!): Mahasiswa
  semuaMahasiswa(prodi: String): [Mahasiswa!]!
}

type Mutation {
  daftarMahasiswa(input: MahasiswaInput!): Mahasiswa!
  hapusMahasiswa(id: ID!): Boolean!
}

input MahasiswaInput {
  nim: String!
  nama: String!
  email: String!
  prodiId: ID!
}

Tanda ! = wajib (non-null). [Nilai!]! = array wajib berisi elemen wajib. = 10 = default value untuk argumen.

Contoh Query — Mengambil Data

Klien — Query dengan argumen & alias 
query DetailMahasiswa($id: ID!) {
  mhs: mahasiswa(id: $id) {       # alias 'mhs'
    nim
    nama
    prodi {
      nama
      jenjang
    }
    nilaiTerbaru: nilai(limit: 3, sort: "-tanggal") {
      mataKuliah
      nilai
    }
  }
}

Variabel $id dikirim terpisah di body request (mirip prepared statement) — mencegah injection dan memudahkan reuse query yang sama.

Contoh Mutation — Mengubah Data

Klien — Mutation create mahasiswa 
mutation BuatMahasiswa($data: MahasiswaInput!) {
  daftarMahasiswa(input: $data) {
    id        # field yang ingin kita terima sebagai konfirmasi
    nim
    nama
  }
}

REST vs GraphQL — Kapan Pilih Mana?

Aspek REST GraphQL
Jumlah endpointBanyak (satu per resource)Satu — biasanya /graphql
Ukuran responseTetap (semua field)Tepat sesuai permintaan klien
Round-trip data terkaitMultipleSatu
Caching HTTPNative (GET cacheable)Sulit (semua POST)
Status codeBermakna (200, 404, 422, ...)Selalu 200; error di field errors
File uploadSederhana (multipart)Perlu extension (graphql-upload)
ToolingUniversal (curl, browser)Apollo, Relay, GraphiQL — perlu setup
Cocok UntukAPI publik, microservice komunikasi internal, layanan sederhanaMobile/SPA dengan banyak layar berbeda, BFF (Backend-for-Frontend)
GraphQL Bukan Pengganti Universal

GraphQL bersinar saat aplikasi punya banyak layar dengan kebutuhan data berbeda-beda. Untuk API kecil (3-5 resource sederhana) atau API publik untuk developer eksternal, REST + OpenAPI seringkali lebih praktis. Pilih tool berdasarkan masalah, bukan tren.

Tools yang Akan Kita Pakai

  1. Apollo Server — Library Node.js untuk membangun GraphQL server. Akan kita praktikkan di Pertemuan 10.
  2. GraphiQL / Apollo Playground — UI di browser untuk menjelajahi schema, autocomplete query, dan menjalankan request — mirip Postman untuk GraphQL.
  3. Lighthouse — Library populer untuk membangun GraphQL server di Laravel (alternatif jika Anda tetap ingin di ekosistem PHP).
