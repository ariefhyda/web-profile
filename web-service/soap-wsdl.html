Sebelum REST berjaya, dunia web service didominasi oleh SOAP — protokol formal berbasis XML yang dirancang untuk komunikasi enterprise. Meski namanya terdengar "kuno", SOAP masih hidup dan dipakai luas di sektor perbankan, asuransi, telco, dan integrasi sistem pemerintahan. Memahami SOAP & WSDL adalah modal wajib bagi developer yang berhadapan dengan sistem warisan.

Capaian Pertemuan Ini

Mahasiswa mampu (1) menjelaskan posisi SOAP dalam evolusi web service, (2) membaca struktur SOAP Envelope, (3) memahami fungsi WSDL sebagai kontrak layanan, dan (4) memutuskan kapan SOAP masih relevan dibanding REST.

Sejarah Singkat: Mengapa SOAP Ada?

SOAP (Simple Object Access Protocol) dirilis Microsoft & tim XML Working Group pada akhir 1990-an, dibakukan W3C pada 2003. Tujuannya: menyediakan protokol terstandar untuk memanggil prosedur jarak jauh (Remote Procedure Call) di lingkungan enterprise — di mana sistem warisan COBOL, Java, dan .NET harus saling berbicara dengan jaminan kontrak yang ketat.

SOAP membawa "berkah" yang sekaligus jadi "kutukan": sangat formal. Setiap pesan dibungkus XML dengan envelope, header, dan body. Setiap layanan punya WSDL — file XML yang menggambarkan setiap operasi, tipe data, dan endpoint. Hasilnya: kontrak super jelas, tetapi pesan jadi besar dan kompleks.

📄
Analogi: Surat Resmi Berkop Kementerian

REST seperti pesan WhatsApp ke teman — cepat, ringkas, langsung ke pokok. SOAP seperti surat resmi kementerian: ada kop, nomor surat, tembusan, lampiran, tanda tangan, stempel. Lebih lambat dan ribet, tapi sah secara hukum dan dapat diaudit. Bank dan asuransi memilih SOAP karena alasan terakhir ini.

Anatomi SOAP Envelope

Setiap pesan SOAP — baik request maupun response — wajib dibungkus dalam struktur Envelope. Di dalam envelope ada Header opsional (untuk metadata seperti otentikasi atau routing) dan Body wajib (berisi pemanggilan operasi atau data balasan):

SOAP Envelope
Header (opsional) 
<soap:Header>
  <auth:Credentials>
    <auth:Username>admin</auth:Username>
    <auth:Token>eyJhbGc...</auth:Token>
  </auth:Credentials>
</soap:Header>
Body (wajib) 
<soap:Body>
  <tns:GetMahasiswa>
    <tns:NIM>22550111</tns:NIM>
  </tns:GetMahasiswa>
</soap:Body>

Contoh Lengkap: SOAP Request & Response

Berikut request untuk memanggil operasi GetMahasiswa di sebuah service akademik:

SOAP Request — POST /akademik 
<?xml version="1.0"?>
<soap:Envelope
    xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"
    xmlns:tns="http://kampus.ac.id/akademik">
  <soap:Body>
    <tns:GetMahasiswa>
      <tns:NIM>22550111</tns:NIM>
    </tns:GetMahasiswa>
  </soap:Body>
</soap:Envelope>

Server akan menjawab dengan envelope serupa, berisi data mahasiswa:

SOAP Response — 200 OK 
<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <tns:GetMahasiswaResponse xmlns:tns="http://kampus.ac.id/akademik">
      <tns:Mahasiswa>
        <tns:NIM>22550111</tns:NIM>
        <tns:Nama>Siti Aisyah</tns:Nama>
        <tns:Prodi>Teknik Informatika</tns:Prodi>
        <tns:IPK>3.72</tns:IPK>
      </tns:Mahasiswa>
    </tns:GetMahasiswaResponse>
  </soap:Body>
</soap:Envelope>

SOAP Fault — Cara SOAP Mengeluh

Jika terjadi error, SOAP tidak memakai HTTP status code seperti REST. Sebagai gantinya, response berisi elemen khusus <soap:Fault> di dalam Body. Empat sub-elemen utamanya: faultcode, faultstring, faultactor, dan detail.

SOAP Fault — NIM tidak ditemukan 
<soap:Body>
  <soap:Fault>
    <faultcode>soap:Client</faultcode>
    <faultstring>NIM tidak ditemukan</faultstring>
    <detail>
      <errorCode>404</errorCode>
      <errorNIM>99999999</errorNIM>
    </detail>
  </soap:Fault>
</soap:Body>

Apa itu WSDL?

WSDL (Web Services Description Language) adalah "kontrak" sebuah SOAP service — sebuah file XML yang mendeskripsikan: operasi apa yang tersedia, input/output tiap operasi, tipe data, dan di alamat mana service bisa dipanggil. Klien membaca WSDL untuk tahu bagaimana cara memanggil service — bahkan banyak IDE (Visual Studio, Eclipse) bisa auto-generate kode klien dari sebuah URL WSDL.

📋
Analogi: Menu Restoran

WSDL adalah menu restoran yang sangat detail: nama setiap hidangan (operasi), bahan-bahan yang harus disediakan tamu (input), bentuk hidangan jadi (output), dan alamat dapur (endpoint). Tamu tidak perlu menebak — semua tertulis dengan format baku.

Struktur Utama WSDL

Sebuah dokumen WSDL terdiri dari lima elemen kunci. Mengenal nama dan peran masing-masing membuat Anda bisa membaca WSDL apa pun:

<types>
Definisi tipe data (biasanya XSD) — misal struktur Mahasiswa, Nilai.
<message>
Pesan abstrak — input atau output sebuah operasi, terdiri dari satu atau lebih bagian (parts).
<portType>
Kumpulan operasi (mirip "interface" di OOP) — daftar method tanpa peduli protokol transport.
<binding>
Menentukan bagaimana operasi dipetakan ke protokol nyata (biasanya SOAP over HTTP).
<service>
Alamat fisik (URL/port) di mana service dapat diakses. Satu service bisa punya beberapa port.

Contoh WSDL Sederhana

akademik.wsdl 
<definitions name="AkademikService"
    targetNamespace="http://kampus.ac.id/akademik"
    xmlns:tns="http://kampus.ac.id/akademik"
    xmlns="http://schemas.xmlsoap.org/wsdl/">

  <!-- 1. Tipe data -->
  <types>
    <xsd:schema targetNamespace="http://kampus.ac.id/akademik">
      <xsd:element name="NIM" type="xsd:string"/>
      <xsd:element name="Mahasiswa">...</xsd:element>
    </xsd:schema>
  </types>

  <!-- 2. Pesan input/output -->
  <message name="GetMahasiswaRequest">
    <part name="NIM" element="tns:NIM"/>
  </message>
  <message name="GetMahasiswaResponse">
    <part name="Mahasiswa" element="tns:Mahasiswa"/>
  </message>

  <!-- 3. Daftar operasi -->
  <portType name="AkademikPort">
    <operation name="GetMahasiswa">
      <input message="tns:GetMahasiswaRequest"/>
      <output message="tns:GetMahasiswaResponse"/>
    </operation>
  </portType>

  <!-- 4. Binding ke SOAP/HTTP -->
  <binding name="AkademikBinding" type="tns:AkademikPort">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http"/>
    <operation name="GetMahasiswa">...</operation>
  </binding>

  <!-- 5. Alamat layanan -->
  <service name="AkademikService">
    <port name="AkademikPort" binding="tns:AkademikBinding">
      <soap:address location="https://api.kampus.ac.id/akademik"/>
    </port>
  </service>
</definitions>

SOAP vs REST — Perbandingan Mendalam

Aspek SOAP REST
Format XML wajib (envelope) JSON, XML, plain text — bebas
Protokol Transport HTTP, SMTP, JMS, TCP HTTP saja
Kontrak WSDL — sangat ketat, machine-readable OpenAPI/Swagger — opsional, lebih longgar
Ukuran Payload Besar (XML + envelope overhead) Ringan (terutama dengan JSON)
Caching Sulit — semua POST Native — GET bisa di-cache
Keamanan WS-Security (built-in, level pesan) HTTPS + JWT/OAuth (level transport)
Transaksi WS-AtomicTransaction — dua/lebih service bisa rollback bersama Tidak ada standar; harus dirakit sendiri
Cocok Untuk Perbankan, asuransi, BPJS, sistem warisan Mobile app, SPA, public API modern

Kapan Anda Masih Akan Bertemu SOAP?

  1. Integrasi Perbankan — Hampir semua API host-to-host bank (transfer, inquiry saldo) masih SOAP karena kebutuhan audit dan transaksi atomik.
  2. BPJS & Sistem Pemerintah — Layanan klaim BPJS Kesehatan, Dukcapil, dan beberapa portal pemerintah masih menyediakan endpoint SOAP.
  3. Telco & Billing — Sistem OSS/BSS di operator seluler banyak yang berbasis SOAP.
  4. ERP Lama — SAP, Oracle EBS dengan versi lawas sering mengekspos service-nya sebagai SOAP.
  5. Integrasi Cross-Vendor — Saat dua perusahaan berbeda harus berbagi data dengan kontrak hukum jelas, WSDL sering jadi pilihan karena ketegasannya.
Jangan Mulai Project Baru dengan SOAP

Untuk aplikasi baru tahun 2026 — terutama yang melayani mobile/SPA — pilihlah REST atau GraphQL. SOAP hanya rasional jika Anda terpaksa berintegrasi dengan sistem warisan yang sudah ada. Memulai project baru dari nol dengan SOAP akan membuat tim Anda lambat dan kesulitan mencari talenta yang menguasainya.
