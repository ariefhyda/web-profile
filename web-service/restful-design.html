Banyak API mengaku "RESTful" tetapi sebenarnya hanya REST aroma — pakai HTTP & JSON, lalu menyebut diri REST. Padahal REST memiliki 6 batasan (constraints) yang dirumuskan Roy Fielding dalam disertasinya (2000). Memahaminya membuat Anda bisa membedakan API yang benar-benar REST dari yang sekadar "JSON over HTTP", dan merancang API yang konsisten serta enak dipakai klien.

Capaian Pertemuan Ini

Mahasiswa mampu (1) menjelaskan 6 constraints REST, (2) menerapkan konvensi penamaan URI yang konsisten, (3) memilih status code dengan tepat, dan (4) mengidentifikasi level Richardson sebuah API.

6 Constraints REST

1
Client-Server
Klien dan server terpisah tegas — boleh berevolusi sendiri-sendiri selama kontrak interface tetap.
2
Stateless
Setiap request berdiri sendiri. Server tidak menyimpan sesi — semua info untuk memproses ada di request.
3
Cacheable
Response harus menandai dirinya cacheable atau tidak (header Cache-Control, ETag).
4
Uniform Interface
Konsistensi global: resource-oriented URI, HTTP methods bermakna seragam, representasi standar.
5
Layered System
Klien tidak tahu apakah ia bicara langsung ke server, ke load balancer, atau ke proxy cache.
6
Code on Demand (opsional)
Server boleh mengirim kode (JS) yang dijalankan klien. Hanya constraint yang opsional.

Stateless — Constraint yang Paling Sering Dilanggar

Stateless berarti server tidak menyimpan state sesi klien antar request. Identitas user, preferensi, konteks — semua harus dikirim oleh klien di setiap request (biasanya via token di header Authorization).

🎫
Analogi: Karcis Kereta

Kondektur tidak menghafal wajah penumpang. Setiap kali ia datang, Anda tunjukkan tiket. Tiket itu sudah berisi semua info: kelas, nomor kursi, asal-tujuan. Kondektur memproses tanpa perlu mengingat siapa Anda dari stasiun sebelumnya. Itulah stateless.

Keuntungan praktis: server bisa di-scale horizontal tanpa session sticky. Request user yang sama di waktu berbeda boleh dilayani server berbeda. Kelas penyimpan state (session in-memory) adalah musuh utama RESTful API.

URI Naming Convention

URI adalah "wajah" API Anda. URI yang konsisten membuat developer lain bisa menebak endpoint tanpa buka dokumentasi. Berikut perbandingan yang sering ditemui:

GET /getMahasiswa
GET /mahasiswa
POST /createMahasiswa
POST /mahasiswa
GET /mahasiswa?id=12
GET /mahasiswa/12
GET /Mahasiswa_List
GET /mahasiswa
DELETE /mahasiswa/12/delete
DELETE /mahasiswa/12
GET /mahasiswa/12/getNilai
GET /mahasiswa/12/nilai

7 Aturan Praktis Desain URI

  1. Gunakan kata benda jamak (plural) — /mahasiswa, /orders, /products. Konsisten di seluruh API.
  2. Jangan masukkan kata kerja — Method HTTP sudah menyatakan aksi. POST /users sudah berarti "buat user".
  3. Gunakan path untuk hierarki — /users/12/orders/5/items. Maksimal 2-3 tingkat agar tetap nyaman dibaca.
  4. Gunakan query string untuk filter, sort, pagination — ?status=active&sort=-created_at&page=2&per_page=20.
  5. Lowercase + tanda hubung — /order-items, bukan /OrderItems atau /order_items.
  6. Jangan akhiri dengan slash — /users, bukan /users/. Konsistensi mencegah redirect 301.
  7. Versi di prefix — /api/v1/users. Memudahkan transisi saat breaking change.

Query String untuk Filter, Sort, & Pagination

Contoh URL canggih 
# Filter: mahasiswa aktif di prodi TI
GET /api/v1/mahasiswa?status=active&prodi=TI

# Sort: tanggal daftar terbaru dulu (- = descending)
GET /api/v1/mahasiswa?sort=-created_at

# Pagination: halaman 2, 20 item per halaman
GET /api/v1/mahasiswa?page=2&per_page=20

# Field selection: hanya ambil nama & IPK (hemat bandwidth)
GET /api/v1/mahasiswa?fields=nim,nama,ipk

# Pencarian teks
GET /api/v1/mahasiswa?search=arif

Memilih Status Code yang Tepat

Operasi Sukses Gagal Umum
GET ambil satu 200 OK 404 Not Found
GET ambil daftar 200 OK (array, bisa kosong) 200 OK dengan array kosong, jangan 404
POST buat baru 201 Created + header Location 422 Unprocessable Entity (validasi)
PUT / PATCH update 200 OK + body baru, atau 204 No Content 404 jika resource tak ada, 409 jika konflik
DELETE 204 No Content 404 Not Found

Richardson Maturity Model

Leonard Richardson mengusulkan 4 level kematangan REST untuk mengukur seberapa "REST" sebuah API. Banyak API komersial berhenti di Level 2 — dan itu sudah dianggap "RESTful" dalam praktik industri.

LEVEL 0 The Swamp of POX (Plain Old XML)
Semua request POST ke satu URL. Server mengandalkan body untuk tahu operasi apa yang diminta. Persis seperti SOAP atau XML-RPC. Tidak memanfaatkan HTTP sama sekali.
POST /api → body: { "action": "getMahasiswa", "id": 12 }
POST /api → body: { "action": "createOrder", ... }
LEVEL 1 Resources
Mulai mengenal "resource" — endpoint berbeda untuk hal berbeda. Tapi masih pakai 1 method (biasanya POST) untuk semua operasi.
POST /api/mahasiswa/get → { "id": 12 }
POST /api/mahasiswa/create → { "name": "..." }
LEVEL 2 HTTP Verbs & Status Codes (target praktis industri)
Memanfaatkan GET/POST/PUT/DELETE sesuai semantiknya, dan status code yang konsisten. Inilah yang umum disebut "REST API" di proyek nyata.
GET /api/mahasiswa/12 → 200 OK
POST /api/mahasiswa → 201 Created
PATCH /api/mahasiswa/12 → 200 OK
DELETE /api/mahasiswa/12 → 204 No Content
LEVEL 3 HATEOAS (Hypermedia as the Engine of Application State)
Response menyertakan link ke aksi-aksi terkait. Klien dapat "berkelana" di API tanpa hard-code URL. Sangat REST-purist; jarang sepenuhnya diadopsi karena overhead.
GET /api/mahasiswa/12 → {
  "nim": "22550111", "nama": "...",
  "_links": {
    "self": { "href": "/api/mahasiswa/12" },
    "nilai": { "href": "/api/mahasiswa/12/nilai" },
    "hapus": { "href": "/api/mahasiswa/12", "method": "DELETE" }
  }
}

Versioning API

Cepat atau lambat, API Anda akan butuh perubahan yang merusak kompatibilitas (breaking change). Tiga strategi versioning populer:

  1. URL versioning — /api/v1/users. Paling jelas, paling cache-friendly, paling populer.
  2. Header versioning — Accept: application/vnd.kampus.v1+json. Lebih "REST-purist" tapi sulit di-debug dengan browser.
  3. Query string versioning — /api/users?v=1. Sederhana tetapi mengotori URL.

Tujuan Realistis Sebuah Tim

Untuk proyek akademik dan kebanyakan proyek industri, capailah Level 2 dengan konsisten — itu sudah membuat API Anda profesional & mudah diintegrasikan. Level 3 (HATEOAS) lebih cocok untuk API publik berumur panjang seperti GitHub atau PayPal.
