Kita sudah menyebut "microservices" sejak Pertemuan 1. Sekarang waktunya mengupasnya tuntas. Microservices adalah gaya arsitektur di mana sebuah sistem dipecah menjadi layanan-layanan kecil yang mandiri, masing-masing punya tanggung jawab fokus, database sendiri, dan dideploy independen. Pendekatan ini memungkinkan tim ratusan engineer bekerja paralel tanpa saling menabrak — tapi membawa kompleksitas operasional yang harus disadari.

Capaian Pertemuan Ini

Mahasiswa mampu (1) menjelaskan karakteristik microservices, (2) menguraikan untung-rugi dibanding monolith, (3) memilih strategi dekomposisi yang tepat (DDD bounded context), dan (4) mengenali anti-pattern distributed monolith.

6 Karakteristik Microservices yang Sebenarnya

  1. Single Responsibility — Satu service = satu kapabilitas bisnis (mis. Inventory, bukan "miscellaneous"). Aturan praktis Sam Newman: "satu service muat dipahami satu kepala dalam dua minggu".
  2. Database per Service — Setiap service punya database sendiri. Tidak boleh service lain query langsung ke DB ini — harus lewat API. Inilah pemisah paling penting.
  3. Independent Deployment — Tim Order bisa deploy 10× sehari tanpa mengganggu tim Auth. Tidak ada lagi "deploy hari Jumat".
  4. Decentralized Governance — Tiap tim memilih bahasa, framework, dan tooling yang paling cocok untuk service-nya. Tidak ada paksaan satu stack.
  5. Smart Endpoints, Dumb Pipes — Logika bisnis ada di service, bukan di message bus. Bus hanya mengantar pesan; service yang memutuskan tindakan.
  6. Built for Failure — Asumsi jaringan lambat, service tetangga down, pesan duplikat. Tiap service harus tetap berfungsi (atau gagal anggun) saat dependency-nya mati.

Database per Service — Aturan Emas yang Sulit

Mengapa setiap service harus punya DB sendiri? Karena database bersama = monolith yang menyamar. Saat tim Order ubah schema kolom, tim Inventory bisa rusak — meski kedua service "terpisah".

🏠
Analogi: Rumah Kos

Monolith = rumah satu pintu, semua penghuni pakai dapur, kamar mandi, dan lemari pakaian yang sama → setiap renovasi mengganggu semua orang. Microservices = unit kos terpisah, masing-masing punya dapur & kamar mandi sendiri → satu unit direnovasi, yang lain tidak peduli. Tetapi: lebih mahal, lebih ribet jaga kebersihan kolektif.

Untung & Rugi Microservices

✓ Keuntungan

  • Skalabilitas selektif — scale hanya service yang ramai (mis. Cart pas flash sale), bukan seluruh aplikasi.
  • Teknologi heterogen — tiap service bebas pilih bahasa/DB paling cocok.
  • Fault isolation — service Notification down ≠ Order ikut down.
  • Tim otonom — release independen, tidak menunggu tim lain.
  • Codebase kecil — onboarding engineer baru lebih cepat per service.

✗ Kekurangan

  • Kompleksitas operasional — perlu CI/CD, container, service mesh, monitoring untuk N service.
  • Network latency — komunikasi antar service melalui HTTP/gRPC, jauh lebih lambat dari pemanggilan fungsi internal.
  • Eventual consistency — transaksi lintas service tidak bisa pakai ACID — perlu pola saga / compensation.
  • Distributed debugging — satu request bisa melibatkan 5+ service; tanpa distributed tracing, melacak error itu mimpi buruk.
  • Data duplication — sering perlu menyalin sebagian data ke service lain agar tidak chatty.

Strategi Dekomposisi: Bounded Context (DDD)

Bagaimana memutuskan "mana yang jadi service tersendiri, mana yang tetap bersama"? Pendekatan paling matang adalah Domain-Driven Design (DDD): kelompokkan kode berdasarkan bounded context — batas alami di mana sebuah istilah punya satu makna yang konsisten.

Contoh: di e-commerce, kata "Order" di konteks Cart berarti "keranjang yang belum di-checkout", tapi di konteks Shipping berarti "paket yang sedang dikirim". Itu dua bounded context berbeda → dua service berbeda.

Hukum Conway: "organisasi yang mendesain sistem akan menghasilkan desain yang meniru struktur komunikasinya". Microservices yang baik biasanya mengikuti batas-batas tim — bukan kebalikannya.

Anti-Pattern: Distributed Monolith

Tanda Anda terjebak di Distributed Monolith

Anda terlihat seperti microservices tetapi menderita seperti monolith jika: (1) deploy satu service mewajibkan deploy 3 service lain, (2) semua service share satu database, (3) satu service down → semua ikut down, (4) request user melibatkan 8 service yang saling memanggil sinkron berantai. Lebih buruk dari monolith karena Anda kena kompleksitas operasional tanpa dapat keuntungan independensi.

Pola Transaksi Lintas Service: Saga

Saat satu transaksi bisnis melibatkan beberapa service (mis. checkout: kurangi stok → debit saldo → buat order → kirim notifikasi), Anda tidak bisa pakai BEGIN TRANSACTION ... COMMIT klasik. Polanya: Saga — pecah jadi serangkaian transaksi lokal, masing-masing punya compensating action kalau gagal.

Saga Sederhana — Checkout 
// Sukses path:
1. Inventory.reserve(item, qty)        // kunci stok
2. Payment.debit(user, total)          // potong saldo
3. Order.create(items, total)          // catat order
4. Notification.send("order created")

// Jika langkah 3 gagal → compensate mundur:
2b. Payment.refund(user, total)
1b. Inventory.release(item, qty)

Dua varian: Choreography (tiap service emit event & bereaksi sendiri — desentralisasi) atau Orchestration (satu orchestrator memimpin alur). Akan kita sentuh lebih lanjut di Pertemuan 12 saat membahas Message Broker.

Kapan TIDAK Perlu Microservices?

  1. Tim < 10 engineer — Anda akan menghabiskan lebih banyak waktu mengurus infrastruktur daripada menulis fitur.
  2. Belum tahu batas bisnis yang stabil — Microservices yang dipecah salah lebih sulit digabung ulang. Mulailah monolith, refactor ke modular monolith, pecah saat batas jelas.
  3. Belum punya CI/CD & observability matang — Microservices tanpa otomasi = neraka manual.
  4. Latency super kritis — Komunikasi jaringan menambah ms; trading system / real-time gaming sering tetap monolith.
Rule of Thumb: "Monolith First"

Martin Fowler menulis: "You shouldn't start a new project with microservices, even if you're sure your application will be big enough to make it worthwhile." Bangun monolith dulu sampai batas-batas bisnis jelas. Pecah saat scaling atau tim benar-benar menuntut, bukan karena tren.
