Setelah memahami apa web service, kini kita masuk ke bagaimana ia berbicara. Hampir semua web service modern berkomunikasi melalui satu protokol yang sama: HTTP. Pada pertemuan ini kita akan mengupas HTTP — methods-nya, anatomi request, status codes — dan dua format data paling populer untuk membawa muatan: JSON dan XML.

Capaian Pertemuan Ini

Mahasiswa mampu (1) memilih HTTP method yang tepat untuk operasi data tertentu, (2) membaca dan menyusun anatomi HTTP request/response, (3) menggunakan status code yang benar, dan (4) membedakan kapan menggunakan JSON dan kapan XML.

Apa itu HTTP?

HTTP (HyperText Transfer Protocol) adalah protokol komunikasi request-response berbasis teks yang berjalan di atas TCP. Sederhananya: klien bertanya → server menjawab. Itu saja. Setiap interaksi web — buka halaman, login, kirim chat, panggil API — pada akhirnya adalah satu siklus HTTP.

Karakter HTTP yang penting untuk web service: stateless (server tidak mengingat request sebelumnya — setiap request berdiri sendiri), berbasis teks (mudah dibaca manusia & di-debug), dan fleksibel terhadap muatan (bisa membawa HTML, JSON, XML, gambar, file biner).

📮
Analogi: Surat Pos

Setiap HTTP request seperti satu pucuk surat: ada amplop (header — alamat tujuan, pengirim, jenis isi), ada isi surat (body — data yang dikirim), dan ada cap pos di balasannya (status code — diterima 200, alamat salah 404, kantor tutup 500). Tukang pos (server) tidak ingat surat-surat sebelumnya.

HTTP Methods — Kata Kerja untuk Data

HTTP menyediakan beberapa method yang merepresentasikan niat kita terhadap resource di server. Memilih method yang tepat bukan sekadar gaya — ini menentukan perilaku cache, idempotensi, dan keamanan API Anda.

GET
Mengambil data tanpa mengubah apa pun di server. Bisa di-cache. Tidak boleh ada body.
Idempotent · Safe
POST
Membuat resource baru. Mengubah state server. Body berisi data yang dibuat.
Not Idempotent
PUT
Mengganti seluruh data resource. Kirim ulang sama = hasil sama.
Idempotent
PATCH
Mengubah sebagian field saja. Lebih hemat bandwidth dari PUT untuk update parsial.
Idempotent*
DELETE
Menghapus resource. Setelah berhasil, request berikutnya akan 404.
Idempotent

Idempotent = aman dipanggil berkali-kali dengan hasil akhir yang sama. Safe = tidak mengubah state server. Memahami sifat ini penting saat retry request akibat koneksi buruk.

Anatomi sebuah HTTP Request

Mari kita "bedah" satu request POST untuk membuat user baru. Setiap baris punya peran spesifik:

Request LinePOST /api/users HTTP/1.1
HeaderHost: api.kampus.ac.id
HeaderContent-Type: application/json
HeaderAuthorization: Bearer eyJhbGc...
HeaderAccept: application/json
Body{
  "name": "Budi Santoso",
  "email": "budi@kampus.ac.id",
  "role": "mahasiswa"
}
  1. Request Line — Method (POST), path (/api/users), dan versi HTTP. Ini "kalimat utama" request.
  2. Headers — Metadata: tipe data yang dibawa (Content-Type), tipe data yang diharapkan kembali (Accept), kredensial (Authorization), dan host tujuan.
  3. Body — Muatan data (umumnya JSON). Hanya method yang mengubah state (POST/PUT/PATCH) yang biasanya membawa body.

Anatomi sebuah HTTP Response

Status LineHTTP/1.1 201 Created
HeaderContent-Type: application/json
HeaderLocation: /api/users/42
HeaderCache-Control: no-store
Body{
  "id": 42,
  "name": "Budi Santoso",
  "created_at": "2026-05-25T08:32:11Z"
}

HTTP Status Codes

Status code adalah "ekspresi wajah" server saat menjawab. Tiga digit, dibagi 5 kelas berdasarkan angka pertama. Memakai status code yang konsisten = API Anda mudah diintegrasikan.

200
OK
Berhasil; biasanya untuk GET / PUT / PATCH.
201
Created
Resource baru berhasil dibuat (untuk POST).
204
No Content
Berhasil tanpa body; cocok untuk DELETE.
301
Moved Permanently
Endpoint pindah; klien diarahkan ke URL baru.
304
Not Modified
Data belum berubah sejak request terakhir (cache hit).
400
Bad Request
Format request salah (JSON rusak, field hilang).
401
Unauthorized
Belum login / token salah.
403
Forbidden
Login OK tapi tidak punya hak akses.
404
Not Found
Resource tidak ditemukan.
422
Unprocessable Entity
Validasi data gagal (email bukan format email, dsb).
500
Internal Server Error
Bug di server; bukan salah klien.
503
Service Unavailable
Server overload / sedang maintenance.

Format Pertukaran Data: JSON vs XML

HTTP hanya membawa data — bentuk dan struktur datanya tergantung kita. Dua format paling populer adalah JSON (JavaScript Object Notation) dan XML (eXtensible Markup Language). Mari lihat data yang sama dalam kedua format:

user.json — JSON 
{
  "id": 12,
  "name": "Arif Hidayah",
  "role": "dosen",
  "courses": [
    "Data Mining",
    "Web Service"
  ]
}
user.xml — XML 
<?xml version="1.0"?>
<user>
  <id>12</id>
  <name>Arif Hidayah</name>
  <role>dosen</role>
  <courses>
    <course>Data Mining</course>
    <course>Web Service</course>
  </courses>
</user>

Perbandingan: Kapan Pilih JSON vs XML?

Aspek JSON XML
Verbositas Ringkas (~30% lebih kecil) Banyak tag pembuka/penutup
Parsing Native di JavaScript & mudah di semua bahasa modern Perlu library DOM/SAX, agak verbose
Skema/Validasi JSON Schema (opsional) XSD & DTD — sangat ketat & matang
Tipe Data String, number, bool, null, array, object Semuanya teks; tipe dipaksakan via schema
Atribut/Namespace Tidak ada konsep atribut Mendukung attribute & namespace
Komentar Tidak didukung <!-- komentar -->
Ekosistem Khas REST API, mobile, web modern SOAP, sistem perbankan/asuransi legacy, dokumen kompleks
Aturan Praktis

Untuk REST API baru, hampir selalu pilih JSON: lebih ringan, native di browser, didukung semua framework. XML tetap relevan saat berintegrasi dengan SOAP service warisan (perbankan, BPJS, layanan pemerintah lama) atau dokumen yang butuh validasi schema sangat ketat.

Tips Praktis Memakai HTTP di Web Service

  1. Selalu pakai HTTPS — HTTP polos rawan disadap. HTTPS mengenkripsi seluruh komunikasi.
  2. Jangan masukkan data sensitif di URL — URL ter-log di server, browser history, dan proxy. Pakai header atau body.
  3. Gunakan status code yang sesuai — Jangan kirim 200 OK dengan field "error": true. Itu membuat klien tidak bisa retry/cache dengan benar.
  4. Konsisten dengan plural — /api/users bukan /api/user. Bermain sesuai konvensi REST yang akan kita pelajari di Pertemuan 4.
  5. Set Content-Type yang benar — application/json untuk JSON, application/xml untuk XML. Salah Content-Type → server bingung mem-parse.
