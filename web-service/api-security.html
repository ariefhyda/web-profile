API tanpa keamanan = pintu rumah yang dibuka 24 jam. Sebagus apa pun desain endpoint Anda, jika siapa saja bisa mengakses dan memodifikasi data, semuanya runtuh. Pertemuan ini membahas dua pondasi keamanan API: Autentikasi (siapa Anda?) dan Otorisasi (apa yang boleh Anda lakukan?), dengan dua mekanisme yang paling sering ditanya dalam wawancara backend: JWT dan RBAC.

Capaian Pertemuan Ini

Mahasiswa mampu (1) membedakan autentikasi vs otorisasi, (2) memilih antara API Key dan JWT untuk kasus tertentu, (3) menjelaskan anatomi JWT, dan (4) merancang RBAC sederhana di Laravel.

Autentikasi vs Otorisasi — Sering Tertukar

🔐 Autentikasi (AuthN)

Siapa Anda? Memverifikasi identitas pengguna. Contoh: email + password, sidik jari, OTP, JWT, API Key. Output: server tahu user X yang sedang request.

🛡️ Otorisasi (AuthZ)

Apa yang boleh Anda lakukan? Memutuskan akses ke resource. Contoh: hanya admin boleh hapus user, dosen hanya boleh edit nilai kelas miliknya. Berlangsung setelah autentikasi.

🏢
Analogi: Masuk Gedung Kantor

Satpam mengecek KTP/ID-card Anda → ini autentikasi. Setelah masuk, ID-card Anda hanya bisa membuka lantai 5 (HR), tidak bisa lantai 12 (Keuangan) → itu otorisasi. Dua hal berbeda, dilakukan oleh dua mekanisme berbeda.

Cara Autentikasi 1 — API Key

API Key adalah string panjang acak yang dibuatkan untuk seorang konsumen (developer atau aplikasi). Klien menyertakan key di setiap request, biasanya di header. Sederhana, tapi minim fitur.

Request dengan API Key 
GET /api/v1/mahasiswa HTTP/1.1
Host: api.kampus.ac.id
X-API-Key: sk_live_CONTOH_API_KEY_jangan_pakai_yang_asli

Kapan dipakai? Server-to-server (Cron job memanggil API, microservice ke microservice), atau API publik untuk developer pihak ketiga (Stripe, Google Maps, OpenWeather). Tidak cocok untuk user-facing apps karena key statis & sulit menambahkan info user.

Cara Autentikasi 2 — JWT (JSON Web Token)

JWT adalah token stateless berbentuk string base64 yang membawa data user + tanda tangan kriptografi. Berbeda dengan session di server, JWT menyimpan klaim di token itu sendiri — server tidak perlu menyimpan apa-apa untuk memverifikasinya.

Anatomi JWT — Tiga Bagian Dipisah Titik

Sample JWT 
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMiIsIm5hbWUiOiJBcmlmIiwicm9sZSI6ImRvc2VuIiwiZXhwIjoxNzQ4MzQ0NTAwfQ.8q3jK_FxN-2Yz1aBcDeFgHiJkLmNoPqRsTuVwXyZ012
1. Header
{ "alg": "HS256", "typ": "JWT" }
2. Payload (Claims)
{ "sub": "12", "name": "Arif", "role": "dosen", "exp": 1748344500 }
3. Signature
HMACSHA256(
  base64(header)+"."+base64(payload),
  SECRET_KEY
)
  1. Header — algoritma tanda tangan (HS256, RS256) dan tipe token.
  2. Payload — klaim (claims): sub (subject/user id), exp (expiry), iat (issued at), serta custom claims (role, nama, dll). Catatan: payload hanya di-encode base64, BUKAN dienkripsi — siapa saja bisa membacanya.
  3. Signature — hasil HMAC/RSA dari header+payload dengan SECRET_KEY server. Klien tidak punya SECRET, jadi tidak bisa memalsukan signature.

Alur Login dengan JWT

CLIENT → SERVER 1. POST /login dengan email + password
SERVER ⚙ SERVER 2. Cek password → valid → generate JWT (sign dengan SECRET_KEY)
SERVER ← CLIENT 3. Response 200 OK + body { token: "eyJhbGc..." }
CLIENT → SERVER 4. Request berikutnya menyertakan Authorization: Bearer eyJhbGc...
SERVER ⚙ SERVER 5. Verifikasi signature dengan SECRET_KEY, cek exp & klaim → lolos → lanjut handler
SERVER ← CLIENT 6. Response data (atau 401 jika token expired / palsu)

API Key vs JWT — Perbandingan

Aspek API Key JWT
State di Server Wajib lookup ke DB tiap request Stateless — cukup verifikasi signature
Membawa Identitas User Tidak (key milik aplikasi) Ya (claim sub, role, dll)
Expiry Permanen sampai dicabut manual Built-in via klaim exp
Revoke Token Mudah (hapus dari DB) Sulit — perlu blacklist/short expiry
Cocok Untuk Server-to-server, public API developer Aplikasi user-facing (mobile/SPA)

Implementasi: Laravel Sanctum (JWT-style)

Laravel menyediakan Sanctum untuk token-based auth yang sederhana. Mekanismenya mirip JWT (token Bearer di header), namun token disimpan di DB sehingga mudah di-revoke.

Setup & controller login 
# Install (Laravel 11 sudah include via install:api)
php artisan install:api

# app/Http/Controllers/AuthController.php
public function login(Request $req) {
    $data = $req->validate([
        'email' => 'required|email',
        'password' => 'required',
    ]);
    $user = User::where('email', $data['email'])->first();
    if (! $user || ! Hash::check($data['password'], $user->password)) {
        return response()->json(['message' => 'Invalid credentials'], 401);
    }
    $token = $user->createToken('api')->plainTextToken;
    return ['token' => $token, 'user' => $user];
}
routes/api.php — proteksi dengan middleware 
Route::post('/login', [AuthController::class, 'login']);

// Semua route di group ini wajib token valid
Route::middleware('auth:sanctum')->group(function () {
    Route::apiResource('mahasiswa', MahasiswaController::class);
    Route::post('/logout', [AuthController::class, 'logout']);
});

Otorisasi: Role-Based Access Control (RBAC)

Setelah server tahu siapa Anda, ia harus tahu apa yang boleh Anda lakukan. Pola paling populer adalah RBAC — setiap user memiliki role (admin, dosen, mahasiswa), dan setiap endpoint membutuhkan role tertentu.

Endpoint Admin Dosen Mahasiswa
GET /mahasiswa✓ Semua✓ Semua⚠ Diri sendiri
POST /mahasiswa✓✗✗
PATCH /mahasiswa/{id}✓⚠ Diri sendiri⚠ Diri sendiri
DELETE /mahasiswa/{id}✓✗✗
POST /nilai✓✓ Kelas-nya✗

Implementasi RBAC di Laravel

Tambahkan kolom role di tabel users, lalu buat custom middleware:

app/Http/Middleware/CheckRole.php 
class CheckRole {
    public function handle(Request $req, Closure $next, ...$roles) {
        if (! in_array($req->user()->role, $roles)) {
            return response()->json(['message' => 'Forbidden'], 403);
        }
        return $next($req);
    }
}
routes/api.php — kombinasikan dengan auth 
Route::middleware(['auth:sanctum', 'role:admin'])->group(function () {
    Route::post('/mahasiswa', [MahasiswaController::class, 'store']);
    Route::delete('/mahasiswa/{id}', [MahasiswaController::class, 'destroy']);
});

Route::middleware(['auth:sanctum', 'role:admin,dosen'])->group(function () {
    Route::get('/mahasiswa', [MahasiswaController::class, 'index']);
});

Untuk Aturan yang Lebih Halus — Policy

Saat aturan "dosen hanya boleh edit nilai kelas miliknya" tidak bisa dinyatakan dengan role saja, gunakan Policy:

app/Policies/NilaiPolicy.php 
public function update(User $user, Nilai $nilai): bool {
    return $user->role === 'admin'
        || ($user->role === 'dosen' && $nilai->kelas->dosen_id === $user->id);
}

// Di Controller:
$this->authorize('update', $nilai);  // auto 403 jika gagal

Praktik Wajib Keamanan API

  1. HTTPS only — Tanpa HTTPS, token Anda lewat di plain-text dan bisa disadap di WiFi publik. Wajib di production.
  2. Rate Limiting — Batasi request per menit per IP/user (Laravel: throttle:60,1) untuk mencegah brute-force & DoS.
  3. Hash password dengan bcrypt/argon2 — Jangan pernah simpan password plain-text. Laravel pakai bcrypt secara default.
  4. Validasi semua input — Termasuk yang dari query string. SQL injection & XSS biasanya masuk lewat input yang diabaikan.
  5. CORS dikonfigurasi sempit — Whitelist origin yang boleh memanggil API, bukan *.
  6. Token expiry pendek + refresh token — Access token 15 menit, refresh token 7 hari. Bocor → kerugian terbatas.
  7. Jangan log token / password — Bersihkan request body dari field sensitif sebelum tulis log.
Awas: JWT Payload Bisa Dibaca Siapa Saja

JWT hanya di-encode base64, BUKAN dienkripsi. Siapa pun yang punya token bisa membuka di jwt.io dan membaca payload. Jangan masukkan data sensitif (password, NIK, nomor kartu kredit) ke dalam claim. Tanda tangan hanya menjamin integritas (tidak dimodifikasi), bukan kerahasiaan.
