Setelah memecah sistem menjadi banyak service, pertanyaan paling penting muncul: bagaimana mereka saling bicara? Ada dua paradigma besar — Synchronous (tanya, tunggu jawab) dan Asynchronous (lempar pesan, jalan terus). Memilih yang tepat menentukan latensi, ketahanan, dan kompleksitas sistem Anda.

Capaian Pertemuan Ini

Mahasiswa mampu (1) membedakan komunikasi sync vs async, (2) menjelaskan gRPC + Protobuf dan kapan dipakai, (3) memahami konsep message broker (RabbitMQ & Kafka), dan (4) memilih pola yang tepat untuk skenario tertentu.

Dua Paradigma Besar

📞 Synchronous

Klien menunggu jawaban. Mirip telepon: "Halo, ini saldoku berapa?" — lawan harus jawab sekarang. Latensi terikat oleh service paling lambat dalam rantai.

Tools: REST, gRPC, GraphQL.

📮 Asynchronous

Pengirim menitipkan pesan ke broker lalu lanjut bekerja. Mirip mengirim WhatsApp: dibalas kapan-kapan. Pengirim tidak diblokir.

Tools: RabbitMQ, Kafka, AWS SQS, Google Pub/Sub.

Bagian 1 — Synchronous: gRPC

gRPC (oleh Google, 2016) adalah framework RPC modern yang sangat populer untuk komunikasi antar microservice di dalam datacenter. Ia berjalan di atas HTTP/2 dan menggunakan Protocol Buffers (Protobuf) sebagai format pesan binary — jauh lebih ringkas & cepat dari JSON.

  1. HTTP/2 multiplexing — banyak request paralel dalam satu koneksi TCP.
  2. Binary Protobuf — ukuran 5-10× lebih kecil dari JSON setara, parsing cepat.
  3. Strong-typed contract — file .proto jadi kontrak yang di-generate ke kode client/server di banyak bahasa.
  4. Streaming dua arah — server stream, client stream, bidirectional stream — bukan hanya request/response klasik.

Contoh: Mendefinisikan Service dengan Protobuf

mahasiswa.proto 
syntax = "proto3";
package kampus;

service MahasiswaService {
  rpc GetMahasiswa(MahasiswaId) returns (Mahasiswa);
  rpc ListMahasiswa(ListRequest) returns (stream Mahasiswa);  // server streaming
  rpc CreateMahasiswa(stream Mahasiswa) returns (BatchResult);  // client streaming
}

message MahasiswaId {
  string nim = 1;
}

message Mahasiswa {
  string nim = 1;
  string nama = 2;
  string email = 3;
  int32 prodi_id = 4;
  float ipk = 5;
}

message ListRequest {
  string prodi_filter = 1;
}

message BatchResult {
  int32 created = 1;
}

Generate stub: protoc --go_out=. --go-grpc_out=. mahasiswa.proto — keluar kode Go server & client yang siap pakai. Bahasa lain (Python, Java, Node, Dart) juga didukung.

Aturan Praktis

Pakai REST/GraphQL di lapisan paling luar (mobile/web ↔ backend). Pakai gRPC di lapisan dalam (service ↔ service di dalam Kubernetes cluster). Banyak perusahaan punya kombinasi ini — REST gateway di tepi, gRPC di tengah.

Bagian 2 — Asynchronous: Message Broker

Dengan komunikasi sync, jika service tetangga down → request Anda gagal. Dengan message broker, pengirim hanya melempar pesan ke "kotak surat"; konsumen mengambilnya kapan siap. Broker juga otomatis menangani retry, dead-letter queue, fan-out, dll.

📬
Analogi: Kotak Pos Apartemen

Anda mengirim paket ke teman → letakkan di kotak posnya, lanjut hidup. Teman ambil kapan dia sempat. Tidak ada yang menunggu. Kalau dia liburan, paket tetap aman di kotak. Kalau dia ingin paket sama dipakai 3 orang sekaligus, sediakan 3 kotak (fan-out). Itulah message broker.

3 Pola Utama dengan Message Broker

Pola 1 — Work Queue (1-to-1)

Distribusi pekerjaan ke banyak worker. Cocok untuk task berat: kirim email, generate PDF, proses gambar.

Producer→Queue: email→Worker 1
↘Worker 2(satu pesan = satu worker)
↘Worker 3

Pola 2 — Pub/Sub (1-to-many, fan-out)

Satu event di-broadcast ke banyak subscriber. Cocok untuk event domain: "OrderCreated" didengar oleh Inventory, Notification, Analytics, Loyalty — masing-masing bertindak sendiri.

Order Service→Topic: order.created
⤿Inventory
⤿Notification
⤿Analytics
⤿Loyalty

Pola 3 — Request-Reply Async

RPC dengan callback queue. Jarang dipakai langsung — sering dipakai untuk operasi panjang (mis. generate laporan PDF).

Contoh: Publish & Consume di RabbitMQ (Node.js)

producer.js — Order Service mengirim event 
import amqp from 'amqplib';

const conn = await amqp.connect('amqp://localhost');
const ch = await conn.createChannel();
await ch.assertExchange('orders', 'fanout', { durable: true });

const event = {
  type: 'OrderCreated',
  orderId: 'ord-1042',
  userId: 12,
  total: 250000,
  occurredAt: new Date().toISOString(),
};

ch.publish('orders', '', Buffer.from(JSON.stringify(event)), { persistent: true });
console.log('📤 OrderCreated dipublish');
consumer-notif.js — Notification Service mendengarkan 
const conn = await amqp.connect('amqp://localhost');
const ch = await conn.createChannel();
await ch.assertExchange('orders', 'fanout', { durable: true });

// Queue eksklusif untuk service ini
const { queue } = await ch.assertQueue('notification.orders');
await ch.bindQueue(queue, 'orders', '');

ch.consume(queue, (msg) => {
  const event = JSON.parse(msg.content.toString());
  console.log('📥 Kirim notifikasi untuk order', event.orderId);
  ch.ack(msg);  // konfirmasi sukses; pesan dihapus
});

Tambahkan consumer-inventory.js & consumer-analytics.js dengan queue masing-masing — semuanya menerima event yang sama tanpa Order Service tahu siapa saja yang mendengarkan. Inilah loose coupling.

Kapan Sync, Kapan Async?

SkenarioPilihAlasan
Cek stok sebelum checkoutSync (gRPC)User perlu hasil sekarang
Kirim email konfirmasiAsyncUser tidak perlu menunggu SMTP
Ambil profil user untuk renderSync (REST/gRPC)Layar butuh data segera
Update analytics, audit logAsyncTidak kritis untuk response
Generate PDF laporan besarAsyncProses lama; user diberi notifikasi saat selesai
Trigger discount loyaltyAsync (event)Order Service tidak perlu tahu adanya Loyalty Service
Heuristik Sederhana

Tanyakan: "apakah hasil dibutuhkan SEKARANG untuk melanjutkan?" Ya → sync. Tidak → async. Banyak sistem terdistribusi yang skalabel by default async dan hanya pakai sync saat benar-benar harus. Pikirkan async lebih dulu, sync sebagai pengecualian.

Async = Eventual Consistency

Begitu Anda pakai async, data tidak akan konsisten seketika di semua service. UI mungkin perlu memberi tahu user "menunggu beberapa detik". Desain dengan kesadaran ini sejak awal — jangan kaget melihat stok terbaru baru terpantul ke laporan beberapa detik kemudian.

Karena memakai format Protobuf binary di atas HTTP/2 multiplexing
Karena gRPC otomatis di-cache di CDN
Karena gRPC tidak butuh kontrak schema
