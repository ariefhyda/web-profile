Anda sudah punya 5 microservice di production. Suatu pagi, user mengeluh: "checkout error". Service Order bilang "sukses". Service Payment bilang "tidak menerima permintaan". Tanpa observability, Anda akan menghabiskan berjam-jam loncat dari satu log ke log lain untuk merangkai cerita. Pertemuan ini membahas tiga pilar observability yang menyelamatkan tim engineering dari kebingungan tersebut, lalu kita tutup mata kuliah dengan ringkasan padat seluruh 14 pertemuan.

Capaian Pertemuan Ini

Mahasiswa mampu (1) menjelaskan tiga pilar observability, (2) merancang structured logging yang dapat di-aggregate, (3) memahami metrics & distributed tracing, dan (4) merangkum keseluruhan materi semester sebagai persiapan UAS.

Tiga Pilar Observability

📜
Logs
apa yang terjadi

Catatan event berbasis teks dari setiap service. Ideal untuk audit & debugging detail. Tantangan: volume besar & tersebar di banyak instance.

Tools: ELK Stack, Loki, Datadog, CloudWatch

📊
Metrics
seberapa banyak

Angka time-series yang di-agregat: request/detik, latency p95, CPU usage, error rate. Hemat storage, mudah di-dashboard & alerting.

Tools: Prometheus + Grafana, Datadog, New Relic

🔍
Traces
perjalanan request

Jejak satu request saat melintasi banyak service. Ungkap latensi tiap hop & titik error. Wajib untuk debugging microservices.

Tools: Jaeger, Zipkin, Tempo, OpenTelemetry

Pilar 1: Structured Logging

Log lama yang berupa kalimat bebas ("User 12 logged in at 10:30") sulit di-grep di volume besar. Modern logging = JSON terstruktur, sehingga bisa difilter berdasarkan field tertentu di Kibana/Loki.

structured-log.json 
{
  "timestamp": "2026-05-25T08:32:11.421Z",
  "level": "info",
  "service": "order-api",
  "traceId": "a3f5c7d9e1b2",
  "userId": 12,
  "action": "order.created",
  "orderId": "ord-1042",
  "durationMs": 147,
  "message": "Order created successfully"
}

traceId adalah benang merah — sama di semua log dari service berbeda untuk satu request user. Di Kibana, query traceId:a3f5c7d9e1b2 akan menarik seluruh perjalanan request itu lintas service.

ELK Stack — Pipeline Logging Terpusat

  1. Service menulis log JSON ke stdout (best practice container).
  2. Filebeat di tiap node mengirim log ke Logstash atau Elasticsearch.
  3. Logstash meng-enrich (parse, tambahkan field, drop noise).
  4. Elasticsearch menyimpan & meng-index untuk pencarian cepat.
  5. Kibana menyediakan UI untuk search, dashboard, dan alerting.

Alternatif modern yang lebih ringan: Grafana Loki — tidak meng-index isi log (cuma label), jauh lebih murah untuk volume besar.

Pilar 2: Metrics dengan Prometheus

Prometheus men-scrape endpoint /metrics di tiap service secara berkala (default 15 detik). Service mengekspos metrik dalam format teks sederhana:

GET /metrics — output dari service 
# HELP http_requests_total Total HTTP requests received
# TYPE http_requests_total counter
http_requests_total{service="order-api",method="GET",status="200"} 14823
http_requests_total{service="order-api",method="POST",status="201"} 3201
http_requests_total{service="order-api",method="POST",status="422"} 142

# HELP http_request_duration_seconds Request latency histogram
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 8123
http_request_duration_seconds_bucket{le="0.5"} 14201
http_request_duration_seconds_bucket{le="+Inf"} 14987

Prometheus menyimpan time-series ini. Lalu di Grafana, Anda bisa membuat dashboard dengan query PromQL — misal latency p95 per service:

PromQL examples 
# Error rate 5 menit terakhir
rate(http_requests_total{status=~"5.."}[5m])

# Latency p95
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))

# Memory pakai > 80% — basis untuk alert
process_resident_memory_bytes / process_memory_limit_bytes > 0.8

OpenTelemetry — Standar Tunggal untuk Observability

OpenTelemetry (OTel) adalah standar terbuka yang menggabungkan API, SDK, dan agent untuk mengumpulkan ketiga pilar dalam format yang konsisten. Anda menulis instrumentation sekali, lalu kirim ke vendor mana pun (Jaeger, Datadog, New Relic). Inilah arah industri saat ini.

Instrumentasi otomatis (Node.js) 
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';

const sdk = new NodeSDK({
  serviceName: 'order-api',
  traceExporter: new OTLPTraceExporter({
    url: 'http://jaeger:4318/v1/traces',
  }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
// Semua request HTTP, query DB, dan call gRPC otomatis ter-trace

Health Check & Alert

  1. Liveness probe — Apakah service masih berjalan? Endpoint /health sederhana. Kalau gagal → orchestrator restart container.
  2. Readiness probe — Apakah siap melayani request? (DB connection OK, cache warmed). Kalau gagal → traffic tidak dirutekan ke instance ini.
  3. Alert berdasarkan SLO — Bukan "CPU 80%", tapi "error rate > 1% selama 5 menit" atau "p95 latency > 500ms" — yang sungguh user rasakan.
  4. Runbook — Tiap alert wajib punya dokumen "kalau ini berbunyi, lakukan ini". Tanpa runbook, alert hanya bikin tim panik.
